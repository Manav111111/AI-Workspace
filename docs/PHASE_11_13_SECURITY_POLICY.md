# Avtaar AI Control Plane — Phase 11–13 Security & Governance Policy

## 1. Scope & Objective

This policy defines the security invariants, tenant data isolation boundaries, secret sanitization protocols, and governance guardrails enforced by the Avtaar AI Control Plane across Phases 11, 12, and 13.

The AI Control Plane handles sensitive operational metadata, customer prompt telemetry, token billing ledgers, and audit trails. The rules specified herein are non-negotiable and enforced at the database, service, and API gateway tiers.

---

## 2. Strict Multi-Tenant Data Isolation

### 2.1 Database Partitioning Rules
Every table introduced in Phase 11–13 MUST enforce tenant isolation via an indexed `company_id` foreign key referencing `companies(id) ON DELETE CASCADE`:
1. `trace_summaries`: Scoped to `company_id`.
2. `audit_events`: Scoped to `company_id`.
3. `playground_sessions`: Scoped to `company_id`.
4. `playground_messages`: Scoped to `company_id`.
5. `usage_ledger_entries`: Scoped to `company_id`.
6. `usage_budgets`: Scoped to `company_id`.

### 2.2 Query Construction Invariants
- Direct primary key lookups (e.g. `SELECT * FROM trace_summaries WHERE trace_id = :id`) are strictly prohibited unless combined with tenant filtering (`WHERE trace_id = :id AND company_id = :tenant_company_id`).
- When a user attempts to access or modify a resource belonging to a different tenant, the API must return `HTTP 404 NOT_FOUND` (rather than `HTTP 403 FORBIDDEN`) to prevent company ID enumeration and metadata probing.

### 2.3 Cross-Tenant Unit Test Proofs
The automated test suite (`tests/test_observability.py`, `tests/test_playground.py`, `tests/test_usage_and_budgets.py`) explicitly creates multi-tenant fixtures (Tenant Alpha and Tenant Beta) and asserts that:
- Traces generated by Tenant Alpha are invisible to Tenant Beta.
- Audit logs generated by Tenant Alpha cannot be retrieved or filtered by Tenant Beta.
- Playground sessions cannot be inspected, messaged, or deleted across tenant boundaries.
- Usage ledgers and budget policies remain strictly segregated.

## 3. Append-Only Immutability Guarantees

### 3.1 Financial & Audit Inviolability
The `audit_events` and `usage_ledger_entries` tables represent authoritative compliance records:
- **No Update Endpoints**: The REST API exposes zero `PUT`, `PATCH`, or edit routes for audit logs or usage entries.
- **No Delete Endpoints**: No tenant or user has permission to delete historical usage ledger entries or audit events.
- **Automated Timestamping**: Record timestamps (`created_at`) are generated server-side using UTC clocks; client-supplied timestamps are ignored.

### 3.2 Audit Event Coverage
The following events are recorded synchronously in the append-only audit trail:
- `AUTH_LOGIN` / `AUTH_SIGNUP`: User authentication events.
- `AGENT_ACTION` / `TOOL_INVOCATION`: Execution of external agent capabilities.
- `BUDGET_OVERRIDE` / `BUDGET_CREATED`: Modification of financial governance rules.
- `BUDGET_EXCEEDED`: Hard limit blocking incidents.
- `PROMPT_MODIFIED` / `CONFIG_UPDATED`: Changes to system prompts or AI employee personalities.
- `PLAYGROUND_SESSION_CREATED`: Initiation of developer sandbox environments.

## 4. Telemetry Sanitization & Secret Redaction

### 4.1 TelemetryRedactor Specification
The `TelemetryRedactor` service intercepts all attributes, prompt payloads, tool inputs/outputs, and error traces prior to database persistence.

#### Case-Insensitive Pattern Matching
The redactor applies precompiled regular expressions against all string values:
- **API Keys**: Google AI Studio keys (`AIza[0-9A-Za-z-_]{35}`), OpenAI keys (`sk-[A-Za-z0-9_-]{20,}`), generic keys (`key-[0-9a-zA-Z]{16,}`).
- **Bearer Tokens**: `Bearer\s+[A-Za-z0-9_\-\.]+`.
- **Basic Auth & Passwords**: `password\s*[:=]\s*[^\s]+`.
- **Payment Cards**: 13–16 digit credit card numbers matching Luhn-valid patterns.
- **Private Keys**: `-----BEGIN [A-Z ]+ PRIVATE KEY-----`.

#### Recursive Key Inspection
When dictionary or list data structures are sanitized, any dictionary key matching the following substrings is instantly masked with `[REDACTED]`:
```python
SENSITIVE_KEYS = {
    "api_key", "apikey", "secret", "password", "token", "access_token",
    "refresh_token", "auth", "authorization", "bearer", "cookie", "private_key",
    "credentials", "client_secret"
}
```

## 5. Distributed Trace Context Security

### 5.1 W3C Traceparent Header Handling
- Upstream HTTP requests may provide a `traceparent` header.
- The `Tracer` parses the incoming header using strict regex validation:
  `^00-([0-9a-f]{32})-([0-9a-f]{16})-([0-9a-f]{2})$`
- If the incoming trace ID is malformed or invalid, the tracer discards it and generates a cryptographically secure random 128-bit trace ID.
- In-memory trace state is stored in `contextvars.ContextVar`, ensuring complete concurrency isolation between parallel coroutines on the same event loop.

## 6. Budget Governance & Resource Exhaustion Defense

### 6.1 Rogue Agent Loop Mitigation
AI employees operating with tool execution loops can inadvertently incur thousands of dollars in LLM API fees if caught in infinite reasoning loops.

### 6.2 Pre-Flight Enforcement
- Before any LLM call or tool execution begins, `BudgetService.check_budget(...)` checks tenant and employee spend against active limits.
- If a hard limit is breached, execution terminates immediately with HTTP 429:
  ```json
  {
    "detail": {
      "code": "BUDGET_EXCEEDED",
      "message": "The configured usage budget 'Monthly Global Token Cap' has been reached."
    }
  }
  ```
- No upstream tokens are spent, protecting the tenant and platform from catastrophic financial loss.
